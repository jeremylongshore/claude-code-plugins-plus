## Why this record exists

Seven user-visible defects were found and fixed in one session. Every one had
been live for **months**, and none was detectable by reading source or by any CI
gate. They were found by probing the deployed site from outside — fetching URLs,
reading response headers, and inspecting computed styles in a real browser.

The individual fixes are in the PRs. What is worth keeping is the *class*: these
defects are invisible to the checks this repo already runs, and will recur unless
someone periodically looks at the served artifact rather than the code that
produces it.

## The three findings worth internalising

### 1. A missing `og:image` breaks nothing, so nothing catches it

`BaseLayout.astro` set `image = "/og-image.png"` and emitted it as `og:image` and
`twitter:image` on every page. The file had **never been committed** —
`git log --all` on that path returned nothing.

Every link preview of the site, on every platform, rendered imageless for five
months. No build failed, no test failed, no lint failed. A missing social image
is invisible to every gate a static-site pipeline normally runs, because nothing
in the build depends on it existing.

Now generated by `scripts/generate-og-image.mjs` and gated by
`--check` in the `validate` job. The gate validates the **PNG bytes** — signature,
IHDR dimensions, minimum size — not merely that a filename exists. An earlier
existence-only version was correctly flagged in review: a check that confirms a
filename rather than its contents reproduces the original failure one level up.

### 2. `X-Frame-Options` and `X-Content-Type-Options` cannot be set from HTML

`BaseLayout` declared three security headers as `<meta http-equiv>`. Browsers
**ignore the first two entirely** — they are response-header-only — and Chrome
logs an error on every page load saying so. `curl -I` confirmed the server sent
none either.

So the site had no clickjacking or MIME-sniffing protection while appearing to
have both. A source-code grep would have found the tags and concluded "handled",
which is precisely why it survived eight months.

Only `<meta name="referrer">` is a valid HTML form. The real headers now come
from Caddy — see `intent-os/ops/ingress/` for the VPS-side record.
`scripts/check-security-headers.mjs` verifies them against the **live response**,
which is the only layer where the answer is real.

### 3. Loading a stylesheet is not the same as applying one

The `/research/` pages linked `/styles/global.css` — a *source* path never copied
to `public/`, so it 404'd. The first fix imported `global.css` properly and added
the webfont, and the built HTML looked correct.

Reading computed values on the deployed page showed it was still wrong:

```
--font-sans : (UNDEFINED)
--bg        : (UNDEFINED)
body font   : "Times New Roman"
body bg     : rgba(0, 0, 0, 0)
```

`tokens.css` was never imported, so every `var(--*)` in `global.css` **and** in
that template's ~300 lines of styles was invalid and dropped. Those six pages had
no design system at all — serif on a transparent background — while loading a
font they never applied.

Root cause is structural: `ResearchTemplate.astro` is a fork of `BaseLayout` that
re-declares `<head>`. That one duplication produced **four** independent
omissions (stylesheet, font, analytics, tokens). Folding it into `BaseLayout`
removes the class; deliberately deferred as a six-page redesign needing its own
visual review.

## Redirect mechanism: why 301s, not Astro `redirects`

The 404 repair initially used Astro's `redirects` config, which emits one thin
HTML page per entry carrying `<meta http-equiv="refresh">`. That took the site
from **3 to 85** instant-redirect pages in a single deploy. Hours later a
consumer network-security filter began blocking `tonsofskills.com`.

**Causation was never established** — Google Safe Browsing reported the domain
clean throughout, and the blocking product is a router-level filter with its own
feed. But a mass of instant meta-refresh pages is the textbook doorway-page
signature such heuristics look for, and meta-refresh is the wrong mechanism
regardless: a permanent redirect belongs in the HTTP status line.

81 now serve as real 301s from Caddy. **Three stay in Astro** —
`scripts/check-routes.mjs` asserts those specific files exist in `dist/`, and
three pages is not the pattern that caused concern. Each redirect has exactly one
owner. Do not move the remaining three without also teaching that gate.

## Follow-ups

- Submit a delisting/review request to the blocking vendor now the doorway-shaped
  pages are gone. Whether it clears is the only available evidence on causation.
- Fold `ResearchTemplate.astro` into `BaseLayout` (removes the four-omission class).
- `permissions-policy` is still absent site-wide — reported as `warn`, not required.
- `/pro/` is the last meta-refresh page; harmless alone.
- The VPS build log is illegible on failure: a pnpm interactive prompt overwrites
  the error with a carriage return, which is why one deploy diagnosis required log
  archaeology. `CI=true` on the VPS build would fix it.
